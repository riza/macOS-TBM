  Open Manual-Review Questions

  From the scanner's research_questions:

  1. How is caller identity established for incoming connections? — Only
  valueForEntitlement: was observed. No audit token extraction, no uid/gid/pid

  2. Is authorization performed per connection or per operation? — 15 granular

  connection-wide check gate everything?
  3. Are audit tokens propagated across IPC boundaries? — The agent is both a
  provider and a client (of AppleAccount daemon, model catalog). Do caller audit
  tokens flow through to these downstream services?
  4. Are entitlement checks operation-specific or coarse? — The 15
  com.apple.ind.* entries suggest per-operation granularity, but manual review
  is needed to confirm each check gates a specific API method.
  5. Does the daemon act as a deputy for another subsystem? — It holds
  com.apple.private.cloudkit.masquerade and com.apple.private.cloudkit.spi, and
  links to AppleAccount, AuthKit, AOSKit. If a client can trigger CloudKit
  operations via IND, the agent may be a deputy for CloudKit.
  6. Which parameters cross from a less-trusted client into privileged 
  operations? — What client-supplied data flows into Keychain operations

  7. All observed clients are root daemons calling current-user — is this

  8. The com.apple.ind.tooling entitlement check suggests a debug/tooling

  ---
  Potential Attack Vectors

  LPE Vector: Unprivileged XPC → Root Keychain Access

  A current-user process (like searchpartyuseragent or assistant_service)
  connects to one of the 12 Mach services. Since no validation is observed, a
  crafted XPC message could potentially reach SecKeyCreateDecryptedData or
  SecItemCopyMatching with root's keychain privileges. The deputy model shows
  searchpartyuseragent already holds com.apple.icloud.searchpartyd.access.

  RCE Vector: Network + Push + Bluetooth

  searchpartyd has NETWORK HIGH and handles APS push notifications. If a crafted
  push triggers a code path that deserializes attacker-controlled data into a
  privileged operation (Keychain, CloudKit, location), this could become remote.
  com.apple.private.cloudkit.masquerade makes this particularly dangerous — it
  can impersonate any CloudKit principal.

  Credential Theft: iCloud Keychain via CKKS

  com.apple.private.ckks (CloudKit Keychain Syncing) allows searchpartyd to
  interact with iCloud Keychain. Combined with com.apple.private.system-keychain
  and SecKeyCreateDecryptedData, this daemon has the keys to decrypt keychain
  items. With zero validation observed, any entitled client could potentially
  trigger keychain operations.

  DOS: 12 Mach Services

  With 12 Mach endpoints and no validation, an unprivileged process could
  exhaust connection limits or crash individual services by sending malformed
  XPC messages.
